TECHNICAL LESSON

A model call can return more than a finished paragraph.

Until now, the shape has been simple: send one input, wait, then print one answer. The same model connection can serve more responsive interfaces, background processing, predictable application data, and conversations that remain manageable as they grow.

01

RESPONSE MODES

Streaming and batching solve different timing problems.

STREAMING

Receive an answer while it is generated.

Normally invoke waits for the complete response. With streaming, the application receives small chunks so a person can start reading a longer answer sooner.

for chunk in groq_model.stream(
    "Explain API-key safety in three sentences."
):
    print(chunk.text, end="", flush=True)

BATCHING

Run independent requests together.

Batching is useful for a list of records, prompts, or tests whose answers do not depend on one another.

batch_responses = groq_model.batch([
    "Define an LLM in one sentence.",
    "Give one use for a low temperature setting.",
])

Streaming changes how the response reaches your application; it does not change what kind of response the model generates. Batching is not conversation memory and is unsuitable when each answer affects the next request.

02

STRUCTURED OUTPUT

Ask for data when your code needs data.

Natural-language prose is easy to read but awkward to place reliably in a database or user interface. A schema gives the application named fields and validation before later code uses the result.

class LessonRecommendation(BaseModel):
    lesson_number: int
    topic: str
    reason: str
    preparation: list[str]

structured_groq_model = groq_model.with_structured_output(
    LessonRecommendation
)
recommendation = structured_groq_model.invoke(
    "Recommend the next lesson for a learner."
)
print(recommendation.topic)

The result is a LessonRecommendation object. Your code can use recommendation.lesson_number or loop over recommendation.preparation. This gives a predictable shape, not automatic factual correctness: facts still need good instructions, trusted data, and appropriate validation.

Worked example: Structured outputs and middleware notebook

03

MESSAGES

A message is text plus a label.

A message is just text plus a label saying who said it.

HumanMessage("How do I create a REST API?")
# label: human, text: "How do I create a REST API?"

Why bother with a label? It lets the model tell which text is a rule and which text is a question.

System message

Application rules: how the model should behave.

Human message

The user’s question or request.

AI message

An earlier model reply carried into the next turn.

Without labels: one blob

groq_model.invoke(
    "Be concise. Always show code. How do I create a REST API?"
)

The model sees one blob of text. It cannot reliably separate our instruction from the user’s actual question.

With labels: rules and question stay separate

groq_model.invoke([
    SystemMessage("Be concise. Always show code."),  # rules
    HumanMessage("How do I create a REST API?"),     # question
])

Now the model can treat the system message as “this is how I should behave” and the human message as “this is what the user wants.”

Real-life example: a system message is the manager’s day-one rule: “Be polite and keep replies short.” A human message is a customer’s question. The employee follows the manager’s rules for every customer without the customer having to repeat them.

Messages also carry history

conversation = [
    SystemMessage("Be concise."),
    HumanMessage("What is Python?"),
    AIMessage("A programming language."),   # earlier model reply
    HumanMessage("Who created it?"),        # “it” means Python
]

Without the earlier messages, the model would not know what “it” means. Labels do not guarantee perfect behaviour, but they give the application and model a clear conversation structure.

04

HISTORY & MEMORY

History is the record; memory is the selection rule.

History is the collection of earlier messages. Memory is the method your application uses to decide what information from that history should be available on the next turn. For a small demo, a Python list is enough:

conversation = [
    SystemMessage("You are a concise assistant for a Python course."),
    HumanMessage("My name is Ada. I am learning about LLMs."),
]

first_response = groq_model.invoke(conversation)
conversation.append(first_response)
conversation.append(HumanMessage(
    "What is my name and what am I learning?"
))

second_response = groq_model.invoke(conversation)

The model knows Ada only because the application sends the earlier messages again. As history grows, input tokens, cost, latency, and eventually context limits grow too. The application needs a rule for what to keep.

05

MIDDLEWARE

Summarise old context; keep recent context in full.

Middleware is code that runs around a model or agent operation. SummarizationMiddleware can watch conversation length, replace older messages with a summary after a threshold, and retain a small number of recent messages alongside it.

SummarizationMiddleware(
    model="groq:openai/gpt-oss-120b",
    trigger=("messages", 10),
    keep=("messages", 4),
)
Older messagescompress after 10
→

→
Recent messageskeep 4 in full

trigger says when summarisation happens; keep says how many newest messages remain in full. A checkpointer, identified by a thread ID, stores conversation state between calls. Summaries save tokens but can lose or distort details, so decide carefully which facts must stay in full history.

Worked examples: Messages, streaming, batching, and memory notebook

CODE EXERCISE · STANDS ON ITS OWN

Make a conversation useful without making it endless.

Task: Build a tiny course assistant that streams its first short reply, stores one human message and one AI reply, and answers a follow-up using that history. Then write down the memory rule you would use after ten turns.

  1. Use stream to display a response as chunks arrive.
  2. Add the completed response and a follow-up question to a message list.
  3. Explain why batching would not be appropriate for the dependent follow-up.
  4. Define what older information you would summarise and what must remain in full.

Learning record: The application can choose a response mode, use structured messages, and make an explicit plan for a growing conversation.

TECHNICAL LESSON

A tool is a function your application makes available.

Tools let a model request information or an action from outside the conversation. The model can propose a useful function and arguments; the software around it remains responsible for execution.

01 · DEFINE A TOOL

Start with a small local lookup.

A tool has a clear name, description, inputs, and output. In a real application it might query a database, read approved documents, check an order, or take an action the user authorised. This local example keeps the focus on the flow.

@tool
def get_course_module(module_number: int) -> str:
    """Return the topic for a course module number from 1 through 6."""
    modules = {
        5: "messages, streaming, batching, and memory",
        6: "tools and tool-execution loops",
    }
    return modules.get(module_number, "That module number is not available.")

The docstring matters: it helps the model understand when the tool is useful and what its input means.

02 · REQUEST, THEN EXECUTE

Bind only permitted tools to the model.

tool_enabled_model = groq_model.bind_tools([get_course_module])
model_message = tool_enabled_model.invoke(messages)

The response may contain tool_calls: structured data describing a requested function and proposed arguments. That does not prove the function ran. Your application must match the request to an allow-list before it executes anything.

for tool_call in model_message.tool_calls:
    requested_tool = tools_by_name.get(tool_call["name"])
    if requested_tool is None:
        tool_result = "This tool is not available."
    else:
        tool_result = requested_tool.invoke(tool_call["args"])

    messages.append(
        ToolMessage(content=str(tool_result), tool_call_id=tool_call["id"])
    )

THE TOOL-EXECUTION LOOP

Send the result back for a normal answer.

The model never automatically calls the function. It hands your application structured information about a function that could help; your application controls whether, how, and with which data that function runs.

03 · KEEP CONTROL

Treat a tool call like untrusted input.

Before executing a real tool, the application should decide whether the requested tool is allowed, whether its arguments are valid, whether the user has permission, how it handles a slow or failed external service, and what it logs for investigation. Models reason about tools; applications own permissions and execution.

CODE EXERCISE · STANDS ON ITS OWN

Build one inspected tool loop.

Define the course-module tool, bind it to a configured chat model, and ask a question that needs module 6. Print or inspect the model’s requested tool call. Execute only a request found in your allow-list, append a ToolMessage, then call the model again for the final answer.

  • Check an unknown tool name returns a clear unavailable result.
  • Keep the tool’s input constrained to the expected argument.
  • Write down which step makes the actual execution decision.

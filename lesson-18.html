A note from me

Ask: “What happened to the grasshopper in winter?” Then ask: “Who helped him?” You know who him means because you just read the conversation. A search system receiving only the second sentence may not.

We already know how to keep messages. Now we need to use that history before retrieval, not just after it. Otherwise the model may have a conversation but receive context about the wrong thing.

What we are building

We use the supplied fables. First rewrite a follow-up as a standalone question, then retrieve story chunks, generate an answer, and save the new turn. The rewrite is a search question, not an answer.

Our path is history + question → standalone question → retrieve → answer → save history. We use one notebook conversation; a production application would keep a separate history for each conversation, as we did with thread IDs in Part II.

The reference shows manual prompts, templates, and older chain helpers. We will keep one clear version using ChatPromptTemplate and MessagesPlaceholder. It lets us see the work without teaching three wrappers for the same flow.

Live runs need GROQ_API_KEY and OPENAI_API_KEY. Run the notebook from its directory; uv sync from the code project installs its dependencies. The embedding model is used for indexing and search, and Groq writes the rewrite and answer.

What did memory change?

It changed the query we sent to retrieval. We did not add every old message to the vector index, and we did not retrain either model. Our application used conversational context to choose a better search input.

Restarting the kernel clears this history and the in-memory index. Longer conversations also need a deliberate history policy; sending everything forever uses more input tokens. We keep that concern separate from this small example.

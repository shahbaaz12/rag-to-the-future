TECHNICAL LESSON

Build the vocabulary before the stack.

AI moves quickly because research, models, tools, and product interfaces all change at once. You do not need to chase every release. Learn the stable request-and-response shape first; later lessons add context, retrieval, validation, and tools around it.

01

THE TERMS

AI, ML, deep learning, and LLMs describe nested ideas.

Artificial intelligence

The broad goal of making software perform tasks associated with intelligence: perception, reasoning, planning, or language.

Machine learning

A way to build some AI systems by learning patterns from data instead of writing every rule by hand.

Deep learning

A family of machine-learning methods that uses multi-layer neural networks, often effective for images, audio, and language.

Large language model (LLM)

A deep-learning model trained to work with language. Given context, it predicts useful next pieces of text and can produce a response.

These labels overlap, but they are not interchangeable. An LLM is one kind of model; an AI application is the software product that uses one or more models.

02

WHERE TO START

Begin with one visible round trip.

An LLM app can be understood as a small circuit: a person asks for help, your application prepares the request, a provider runs a model, and your application receives and presents a response.

Starting here keeps failures understandable. If the answer is poor, inspect the request and response. If a request fails, inspect credentials and provider settings. Once this works, adding several new concepts at once is no longer necessary.

03

TWO USEFUL NAMES

An LLM and a chat model are related, but serve different interfaces.

LLM

Language engine

An LLM accepts text or tokens as context and produces generated output. It can be used for completion, extraction, classification, summarisation, and more.

CHAT MODEL

Conversation interface

A chat model is an LLM exposed through messages with roles such as system, user, and assistant. It is convenient when your app has instructions and a user conversation.

Messages do not give a model permanent memory. Each call only knows the context your application sends. A model also does not automatically know your private notes, current database, or whether an answer is true. Those are application responsibilities.

04

WORKSHOP SETUP

Create a small Python project with uv.

uv’s project initialization guide ↗ explains the generated project files. From an empty folder, initialise the project and add the libraries needed for the first two lessons:

uv init rag-study-assistant
cd rag-study-assistant
uv add langchain langchain-groq langchain-google-genai python-dotenv

langchain supplies the application framework. The Groq and Google GenAI packages provide their chat-model integrations, while python-dotenv loads local environment variables. Add langchain-community later when a lesson actually uses a community integration. OpenAI and Anthropic integrations can also be added later if you choose those providers; they are not required here, and their API access may involve paid usage.

uv records dependencies in pyproject.toml and locks them in uv.lock. If a platform specifically asks for a requirements file, export one instead of maintaining two dependency lists:

uv export --format requirements-txt --output-file requirements.txt

Choose a provider

Follow the official Groq quickstart ↗ or Gemini API key guide ↗ to create and manage a key. Availability and account requirements can change; check the provider’s current documentation.

Keep the key local

# .env — never commit this file
GROQ_API_KEY=your_key_here
# or
GOOGLE_API_KEY=your_key_here

# .gitignore
.env

Do not paste keys into code, screenshots, or chat. If a key is exposed, revoke it in the provider console and create a replacement.

FUTURE CODE EXERCISE · STANDS ON ITS OWN

Task: make one model request.

In a new Python file, load a provider key from .env, create either a Groq or Gemini chat model, and send the message: “Explain HTTP to a beginner in three sentences.” Print the returned text. Then run it a second time and note one similarity and one difference.

  • Input: one fixed user message and one provider key stored outside source code.
  • Expected behaviour: the program either prints a model response or reports a clear request error.
  • Check: no key appears in source control, terminal output, or screenshots.

This exercise deliberately has no conversation history, private documents, tools, or claims of factual verification. Those capabilities arrive after the basic round trip is visible.
